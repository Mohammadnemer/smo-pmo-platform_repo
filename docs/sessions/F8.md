# Session F8

## Session ID

F8

## Scope

Gantt interaction: drag to move, drag to resize duration, drag to draw a dependency,
expand/collapse over the WBS hierarchy, and live reschedule — turning F7's read-only Gantt
into an authoring surface. This is architecture-mvp.md §7's layer 5 ("interaction"), building
on layer 3 (CPM, B6) and layer 4 (rendering, F7).

## Done when

Dragging a task reschedules its dependents in place.

## Prerequisites

- F7 (Gantt rendering) — the virtualized grid + SVG timeline this session adds pointer
  interaction to; `ganttMath.ts`'s date/layout math and `GanttChart.tsx`'s virtualization are
  reused, not replaced.
- B6 (PMO API + CPM engine) — `CriticalPathEngine.cs`'s forward/backward pass and
  `ScheduleQuery.cs`'s stored-schedule pattern, both extended here (not rebuilt).

## Decisions made

- **A per-task "start no earlier than" (SNET) constraint, not a hand-set date.** Before this
  session the CPM engine had *zero* degrees of freedom besides duration and dependency lag —
  every task's start was purely derived from its predecessors back to one project anchor, so
  there was no way to say "this task starts here" independent of its dependency chain. This is
  a domain-model question, not a UI one (new column, new migration, engine semantics), so it
  was flagged and confirmed with the user rather than guessed. `TaskItem.ConstraintStart`
  (`DateOnly?`) is `null` by default (purely dependency-driven, unchanged behaviour);
  `CriticalPathEngine.TaskInput.ConstraintStartDay` floors the forward pass
  (`start = max(constraintFloor, dependencyDrivenStart)`), so a later constraint pushes the
  task and everything downstream of it out, while an earlier one has no effect (a floor, not a
  pin) — dependents reschedule through the *existing* forward pass with no new plumbing.
  Dragging sets it; there's no "clear constraint" affordance yet (see Follow-ups).
- **Resize and move share the existing `PUT /tasks/{id}` endpoint**, not new routes.
  `TaskWriteModel` gained one field (`constraintStart`); the frontend reads a task's current
  `TaskResponse`, spreads it back into a `TaskWriteModel` (`toTaskWriteModel` in
  `ProjectWorkspacePage.tsx`), and overrides just the field the drag changed. This avoids a
  second write endpoint and keeps every task mutation going through the one place
  (`ScheduleQuery.RecomputeAsync`) that already recomputes CPM on every write.
- **Drag-to-link reuses `POST /dependencies` as-is** — no backend change needed; the existing
  in-memory-candidate-graph cycle check already rejects a link that would create a cycle.
- **A dropped weekend constraint degrades gracefully instead of being rejected.** F7 already
  noted the frontend has no view of the tenant's working calendar, so a drag can land on a
  non-working day. Rather than validating that client-side (impossible without the calendar)
  or rejecting it server-side, `WorkingCalendar.WorkingDayIndex` — the new inverse of
  `AddWorkingDays` — resolves any date to the working-day index of the last working day at or
  before it. A Friday/Saturday drop simply floors to Thursday; verified in
  `CriticalPathEngineTests.WorkingDayIndexOnAWeekendResolvesToTheLastWorkingDayAtOrBeforeIt`.
- **No client-side CPM.** A drag's live preview only moves its own bar/ghost (a CSS
  `translateX`, or a width delta for resize) — there is still no JS copy of the engine (F7's
  own decision). The *committed* effect (dependents actually rescheduling) appears once the
  mutation resolves and `useUpdateTask`/`useCreateDependency`'s `onSuccess` invalidates the
  `['pmo','schedule',projectId]` query, triggering a refetch of the server's recomputed
  values. This is what F8's "Done when" line is actually asserting — a drag proving the
  server-side recompute propagates, not a client-side approximation of it.
- **RTL: physical pixels for the live preview, signed days for the commit.** A CSS
  `translateX(deltaPx)` always moves an element by the raw physical pointer delta regardless of
  `dir`, so the ghost bar tracks the cursor for free in both directions with no special-casing.
  Converting that same delta into a day count for the actual mutation *does* need a sign flip
  in RTL (`signedDays` in `GanttChart.tsx`): later dates sit at a *smaller* physical X in RTL
  (the timeline's start edge is on the right), so dragging left is "later" in RTL and "earlier"
  in LTR. Verified in a live RTL browser session: dragging a bar physically left in Arabic
  produced a later `constraintStart`, confirming the sign convention (see How it was verified).
- **Expand/collapse is a WBS-string-prefix hierarchy, not a new parent-task relation.**
  `TaskItem` has no `ParentTaskId` (flat `WbsCode` string, per B6/F6/F7), and adding one was out
  of scope for an interaction-layer session. `computeParentWbsCodes`/`computeVisibleTasks` in
  `ganttMath.ts` instead treat a WBS code as a parent when another task's code is exactly one
  dot-segment deeper and shares its prefix (`"1"` is a parent of `"1.1"`, not of `"1.10"` — the
  trailing-dot check rules that out) — an ancestor-lookup is a `Set` membership test per
  dot-segment (O(depth)), not a scan over every other task, so it's cheap even at F7's 10k-task
  stress scale. Purely a frontend rendering concern; no schema or API change.
- **Two real bugs found and fixed during manual verification, not just during coding:**
  1. `.gantt-bar`'s `overflow: hidden` (needed so the percent-complete fill respects the bar's
     rounded corners) was clipping the resize/link handles, which are deliberately positioned
     partly outside the bar's own box for a comfortable hit target — clipping affects
     hit-testing along with painting, so clicks meant for a handle silently fell through to the
     bar underneath and were misread as a move. Fixed by dropping `overflow: hidden` from the
     bar and giving `.gantt-bar__fill` its own `border-radius` instead, so it still reads as a
     rounded pill without relying on the parent to clip it.
  2. The resize/link handles are children of the bar, which also listens for the same pointer
     events; `setPointerCapture` retargets a handle's `pointerup`/`pointermove` back to the
     handle, but retargeting doesn't stop it from also *bubbling* to the bar's identical
     listener afterwards — every handle-drag was silently double-firing its mutation. Fixed
     with `event.stopPropagation()` in `handleDragMove`/`handleDragEnd`.
  Both were caught by driving the real app end-to-end (see below) rather than by code review —
  worth noting because neither would show up in a type-check or a unit test of `ganttMath.ts`'s
  pure functions.

## Follow-ups

- **No "clear constraint" UI** — once a task is dragged, there's no affordance yet to unpin it
  back to purely dependency-driven scheduling (only another drag that happens to land on the
  same date). A right-click/context-menu "clear" action would be the natural next step; not
  attempted here to keep this session to drag interactions specifically.
- **Gantt row order has no WBS tie-break** — discovered incidentally while verifying
  expand/collapse: `PmoEndpoints.cs`'s `GET /schedule` orders tasks by `ScheduleStart` only (no
  secondary sort), so tasks that tie on the same computed start date (e.g. several unconstrained
  root tasks) can render in an arbitrary order relative to their own WBS siblings/parent. This
  predates F8 (B6/F6's own query) and isn't specific to it — expand/collapse still hides/shows
  the right rows regardless of order — but a future session touching the Gantt should consider
  ordering by WBS code as a secondary sort for a cleaner default view.
- **Constraint doesn't influence the backward pass.** `LateStart`/`LateFinish`/`TotalFloat`
  are still computed exactly as before (from successors and project duration only) — a
  constrained task's float can look unintuitive in edge cases the way it would in any simplified
  CPM implementation without full constraint-aware slack propagation. Accepted as an MVP-lean
  simplification; real PM tools model this more precisely, worth revisiting if float readings on
  heavily-constrained schedules become a real complaint.
- **Milestone link-handle position** — a milestone's link-handle is a child of the diamond
  `<span>`, which carries a `rotate(45deg)` transform (unrotated during a move-drag), so the
  handle sits at a rotated offset rather than pixel-perfectly on the diamond's edge. Cosmetic
  only (still fully clickable) — not chased further given the milestone diamond's small size.
- Dark-theme screenshot verification of the Gantt's new interactive elements is still open —
  same gap F7 already left open for the Gantt generally (token-only styling, low risk).
