# Session X2

## Session ID

X2

## Scope

Track X · Integration & roll-up — "Roll-up worker". An in-process `BackgroundService`
debounces PMO domain events (task % complete, RAID severity, schedule variance), then walks
the graph `project → program → initiative → objective → strategy` and **stores** the computed
health at every level (architecture-mvp.md §5, PRD §5.3/§6.3). Dashboards will read the
stored value only — nothing recomputes on read.

This is the second cross-module feature after X1 (initiative ↔ delivery links). X1 built the
link table; X2 is the reason that table exists.

## Done when

Moving a task's % complete changes its objective's stored health. Verified against an
in-memory integration host that wires the real HTTP surface: creating a task at 20% complete
on a project linked (100% contribution) to an initiative drives that initiative's objective to
`Health = Red, HealthScore = 20`; `PUT`-ing the same task to 100% complete and flushing the
worker's debounce queue drives it to `Health = Green, HealthScore = 100` — read back through
`GET /api/smo/objectives/{id}`, not recomputed by the test.

## Prerequisites

- X1 (initiative ↔ delivery links) for the `InitiativeDeliveryLink` table this session reads.
- B5 (SMO API), B6 (PMO API & scheduler) for the entities and their existing
  `Health`/`HealthScore`/`HealthComputedAt` columns on Initiative/Objective/Strategy.

## Decisions made

- **Program joins the stored-health graph.** PRD §5.3's mermaid diagram
  (`Project -.status roll-up.-> Program -.status roll-up.-> Initiative`) puts Program in the
  middle, even though the PRD's one-line formula ("project % complete + RAID severity +
  schedule variance → initiative delivery health") only names Project. `PmoProgram` gained
  the same `Health`/`HealthScore`/`HealthComputedAt` columns PMO's `Project` gained this
  session (migration `AddDeliveryHealth`) — Program's score is a plain average of its
  projects' stored scores, nothing more.
- **Only Project has a genuinely PMO-specific formula.** `ProjectHealthCalculator` (pure,
  unit-testable without a database) computes a 0-100 score from: a duration-weighted average
  of task `% complete`; a penalty for open RAID items scoped to the project, by severity
  (Critical 25 / High 15 / Medium 5 / Low 2, capped at 40 combined); and a penalty for tasks
  on the critical path (`IsCritical`, PMO's own CPM output) that are incomplete and past their
  stored `ScheduleFinish` (15 each, capped at 40 combined) — the "schedule variance" input.
  Every level above Project (Program, Initiative, Objective, Strategy) is just a
  (weighted) average of its children's already-stored scores — `HealthAggregation` in
  `/Shared`, shared because that math has no module-specific meaning. RAG banding is uniform
  everywhere: ≥80 Green, ≥50 Amber, else Red; no tasks and no open RAID items yet leaves a
  project `NotSet`, matching how a fresh Initiative/Objective/Strategy starts.
- **Roll-up owns the one truly cross-module step; each module cascades its own.** PMO
  recomputes Project → Program internally (both its own tables). SMO sets one Initiative's
  health and cascades to Objective → Strategy internally (all three its own tables, via
  `RecomputeInitiativeHealthCommand`). The only leg that crosses a module boundary end to end
  is Program/Project → Initiative, because only Roll-up's `InitiativeDeliveryLink` table knows
  the `ContributionWeight` needed to combine them — so `RecomputeDeliveryHealthCommandHandler`
  lives in Roll-up, sends `RecomputeProjectHealthCommand` into PMO, reads any *other* linked
  vehicle's already-stored health via `GetProjectHealthQuery`/`GetProgramHealthQuery` (never
  recomputed), and hands the weighted result to SMO. New contracts for all of this
  (`RollupHealthContracts.cs`) live in `/Shared`, same reasoning as X1's `CrossModuleQueries`.
- **The debounce queue lives in `/Worker`, not `/Rollup`.** `/Worker` project-references only
  `/Shared` (T1's rule), so it can't hold a `RollupDbContext`. Its whole job is: receive
  `PmoDeliveryHealthInputsChanged` (a new `/Shared` domain event PMO publishes after every
  task/dependency/RAID write that can move a project's health), debounce per (tenant,
  project), and send one `RecomputeDeliveryHealthCommand` into Roll-up once a pair goes quiet
  for the configured window (`RollupWorker` config section, defaults 2s debounce / 500ms poll).
- **Tests bypass the timer, not the queue.** `IRollupHealthProcessor.ProcessDueAsync` takes
  the debounce window as a parameter; passing `TimeSpan.Zero` drains whatever the queue
  currently holds immediately. The debounce data structure itself (`RollupSignalQueue`) is
  still exercised by real event publishes — only the wall-clock wait is skipped, so the "Done
  when" line doesn't need `Task.Delay` or retry loops to be deterministic.
- **A signal for a project the recompute later finds deleted is a silent no-op.** Between the
  event firing and the debounce window elapsing, the project could be gone;
  `RecomputeProjectHealthCommand` returns `null` and `RecomputeDeliveryHealthCommandHandler`
  just returns. Its stale contribution to any initiative fades out next time that initiative
  recomputes from a different trigger — acceptable for MVP (X4 promotes this queue to Service
  Bus at scale, and deletion-driven recompute isn't in this session's "Done when").
- **RAID items scoped to Portfolio/Program don't trigger a recompute (yet).** Only
  project-scoped RAID create/update/delete publishes the signal — PRD §5.3's formula sentence
  names project-level RAID; program/portfolio-level RAID stays read-only visibility (PRD
  §6.2.6) for now. Noted as a follow-up rather than silently guessed into scope.

## How it was verified

- `dotnet build SmoPmoPlatform.slnx` — clean build; `EnforceModuleBoundaries` passed, confirming
  Roll-up, PMO, SMO still project-reference only `/Shared` despite the new seam, and `/Worker`
  still project-references only `/Shared` too (it holds no module's `DbContext`).
- `dotnet test` on `Rollup.Tests` (11/11 passing, the 7 from X1 plus 4 new): the "Done when"
  line itself (task % complete 20 → Red/20, then 100 → Green/100, read back from
  `GET /api/smo/objectives/{id}` and cross-checked against the Strategy and PMO
  Project/Program `GET`s the graph should also have touched); an open Critical RAID item
  pulling a fully-complete project from Green to Amber (75 = 100 − 25); an initiative's health
  as the contribution-weighted average across two delivery vehicles (100×0.7 + 0×0.3 = 70 →
  Amber, distinguishing this from a plain average); and tenant isolation (recomputing tenant
  A's project never touches tenant B's identically-shaped, still-`NotSet` objective).
- Re-ran `Pmo.Tests` (27 passed / 2 skipped), `Smo.Tests` (27 passed / 2 skipped),
  `Platform.Tests` (5 passed) — no regressions from the new PMO/SMO entities, contracts, or
  endpoint signature changes.
- **Not verified against a real PostgreSQL server in this session** — no reachable Postgres
  and no Docker daemon in this environment (the same reason `Pmo.Tests`/`Smo.Tests`'
  `PostgresRlsTests` stay `[Fact(Skip=...)]` here). The migration follows the exact
  hand-written `AddColumn` pattern `AddTaskConstraintStart` already proved against Postgres
  (B6), but that specific migration has not itself been run against a live server. Flagged
  rather than silently claimed — worth doing before this ships.

## Follow-ups

- X3 (traceability & alignment) will read this session's stored health for the "unaligned
  work" / "unfunded objectives" reports.
- Program/Portfolio-scoped RAID items don't yet feed the roll-up (see "Decisions made") — pull
  in if a session needs portfolio-level health to react to them.
- A deleted project's last-known contribution to an initiative isn't actively cleared, only
  superseded by the next recompute of that initiative from a different trigger — fine for
  MVP, worth revisiting if "delete the only delivery vehicle" turns out to be a common path.
- X4 (p2, Service Bus roll-up) replaces `RollupSignalQueue`'s in-memory debounce with Service
  Bus and splits the worker into its own Container App — the `IMessageBus`/domain-event seam
  this session built should not need to change shape for that move.
- No SPA surface yet — this session is backend + tests only, per CLAUDE.md's "build the named
  session, then stop." The health values are already exposed on every relevant `GET` response
  for whichever frontend session wires up the dashboard.
