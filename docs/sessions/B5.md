# Session B5

## Session ID

B5

## Scope

The SMO API: CRUD for strategy, perspectives, objectives, KPIs and initiatives, plus the read
surface the scorecard needs (KPI historical series, RAG evaluation, and a single aggregate
endpoint that returns the whole scorecard tree).

## Done when

The scorecard's data can be built end to end through the API.

## Prerequisites

- B1–B4: request pipeline and tenant context, authentication, RBAC, mediator + audit interceptor.
- D1–D4: schema foundation, RLS, SMO/PMO tables, tenant seed.

## Decisions made

### 1. API surface — REST resources + aggregate reads (open decision, now closed)

Architecture §12.1 was open between REST, REST + aggregate endpoints, and GraphQL. B5 is the
first session that had to commit, so it was decided rather than guessed and written up as
[ADR 0002](../adr/0002-api-surface.md): REST for all writes and single-resource reads, plus
purpose-built aggregate read endpoints where a view needs a whole subtree. `§12.1` is struck out
in the architecture doc and moved to "recently resolved" in `decisions-open.md`.

Routes: `/api/smo/{strategies|perspectives|objectives|kpis|initiatives}` with
`/api/smo/kpis/{id}/measurements` for actuals, and the one aggregate,
`GET /api/smo/strategies/{id}/scorecard?includeHidden=&trendPoints=`.

### 2. The SMO module now owns its entities and its tables

D3 had put the SMO entities in `/Shared` under `PlatformDbContext`, which contradicts "each
module owns its own EF Core entities and tables". B5 corrected that:

- The entities live in `src/SMO/SmoEntities.cs` (namespace `SmoPmo.Smo`) — the previously
  orphaned file, now the real model.
- `SmoDbContext` maps them to `Smo*`-prefixed tables and keeps its own migration ledger,
  `__EFMigrationsHistory_Smo`, so SMO schema changes ship independently of Platform's.
- The D3 Platform migration no longer creates those five tables; SMO's own initial migration
  does. Table names are prefixed rather than reused, so an existing dev database does not
  collide — see *Follow-ups* for the leftover legacy tables.
- `CreateStrategyCommand` moved from `/Platform` to `/SMO` and now returns the new id.

### 3. Cross-module audit goes through the mediator

Platform owns the audit table, so SMO cannot write it. A new shared
`AuditingSaveChangesInterceptor` stamps tenant/audit metadata and, *after* a successful save,
publishes `EntitiesChangedEvent`; Platform's `EntitiesChangedEventHandler` writes the rows. This
keeps one owner per table and keeps SMO independently testable — publishing is a no-op when
nobody subscribes. `AuditEntries` gained `Module` and `EntityId` columns so a trail can be read
per record.

### 4. Two non-negotiables were only half-true and were fixed

- **RLS on SMO tables.** D2's RLS migration covers Platform tables only; the SMO/PMO tables D3
  added had no policy at all. SMO's migration enables RLS on all six SMO tables with both
  `USING` and `WITH CHECK`, and adds `FORCE ROW LEVEL SECURITY` — without FORCE the policy is
  skipped for the table owner, which is the role the API connects as.
- **`app.tenant_id` reaching Postgres.** Nothing was issuing it, so the RLS predicates would
  have compared against the all-zero guid. A shared `TenantConnectionInterceptor` now sets it on
  every connection both modules open (parameterised via `set_config`, not string-formatted SQL).

### 5. Lifetime fixes that tenant isolation depends on

`ITenantContext` was a singleton — one request's tenant would have been served to every later
request. It is now scoped, which forced two related corrections: `TenantResolutionMiddleware`
takes the tenant context per invocation instead of capturing it in its constructor, and
`IMessageBus` is scoped so the mediator resolves scoped handlers from the request scope rather
than the root provider.

### 6. Domain shape

- KPIs carry the PRD §6.1.4 fields (unit, direction, frequency, baseline, target, actual, RAG
  bands, formula, data source, owner) plus a `KpiMeasurement` series for trend charts. Appending
  a measurement also refreshes the denormalised latest actual, so the scorecard never aggregates
  the series on read.
- **KPI RAG is computed on read; roll-up health is not.** RAG is a single-row calculation from
  that KPI's own target/actual/bands, so it is evaluated in `KpiEvaluation`. Objective,
  initiative and strategy `Health` are graph roll-ups: they are stored fields that only X2
  writes, and the scorecard reads them untouched.
- Every label has an `…Ar` twin (AR/EN from line one), and perspectives carry `DisplayOrder` +
  `IsHidden` for the tenant reordering/hiding in PRD §6.1.2.
- Authorization: SMO endpoints name `SmoReadPolicy`/`SmoWritePolicy`; `/Api` decides who
  satisfies them by extending B3's entity × action matrix with a `Strategy` resource.
- Connection strings moved out of code into `ConnectionStrings:Platform` / `ConnectionStrings:Smo`.

## How it was verified

- `dotnet build SmoPmoPlatform.slnx` — succeeded, 0 warnings. Module boundaries still hold:
  `Directory.Build.targets` fails the build on a module→module reference, and SMO references only
  `/Shared`.
- `dotnet test tests/Smo.Tests` — **24 passed, 0 failed, 2 skipped** (the skipped pair is the
  PostgreSQL suite below); `dotnet test tests/Platform.Tests` — **5 passed, 0 failed**.
- **The acceptance line.** `ScorecardEndToEndTests.ScorecardIsBuiltEndToEndThroughTheApi` builds
  the entire scorecard over HTTP and nothing else: POST strategy → 2 perspectives → 2 objectives
  → 4 KPIs → 6 measurements → 1 initiative, then a single
  `GET /api/smo/strategies/{id}/scorecard`. It asserts perspective ordering, the latest actual
  winning (96 of three points), RAG per KPI (green/amber/red/not-set), lower-is-better
  over-achievement (4 against a target of 5 = 125%), the trend series in period order, the
  Arabic name surviving the round trip, RAG tallies per objective and per strategy, and that
  roll-up `Health` stays `NotSet` because nothing recomputes it on read.
- Tenant isolation at the API layer: two tenants against the same store — tenant B's list is
  empty, its GET is 404, and it cannot attach a perspective to tenant A's strategy.
- RBAC: a `Contributor` reads the scorecard but is 403 on write and delete; an unauthenticated
  caller is 401; a role with no SMO entitlement is 403 even for reads.
- Audit: create/update/delete of a strategy through the API lands three audit rows in
  `PlatformDbContext` with `Module = "SMO"` and the row's `EntityId` — i.e. the cross-module
  audit seam works, and B4's acceptance line is still true through its updated test.
- `KpiEvaluationTests` covers both directions, band boundaries, custom bands, missing
  target/actual, and the zero-target/zero-actual division cases.

### Not verified — live PostgreSQL

`PostgresRlsTests` exercises the migration, real SQL translation and RLS against a server, but it
**did not run**: PostgreSQL is listening on `localhost:5432` yet rejects the credentials the repo
assumes (`postgres/postgres` → `28P01 password authentication failed`), and we chose to defer it.
The two tests are marked `Skip` so they report as skipped rather than as passing — xunit 2.x has
no dynamic skip, and a test that silently returns would have read green while proving nothing. To
close this out: set `SMO_TEST_POSTGRES` to a working connection string and delete the two `Skip`
arguments. The test uses its own database (`smo_pmo_platform_b5test`), which it drops and
re-migrates, so the dev database is untouched.

Worth noting for whoever picks this up: because the connection string was hardcoded to
`postgres/postgres` in code until this session, **no earlier session ever connected to this
PostgreSQL server either** — D1–D4's migrations are equally unproven against it. B5 moved the
connection strings into configuration (`ConnectionStrings:Platform` / `:Smo`), which is what makes
a live run possible at all.

Consequently these remain unproven against a real server: the SMO migration SQL, the RLS
policies (including `FORCE ROW LEVEL SECURITY`), `set_config('app.tenant_id', …)` on a live
connection, and Npgsql translation of the scorecard queries. The in-memory provider accepts LINQ
that Npgsql may not, so this is a real gap, not a formality.

## Follow-ups

1. **Run `PostgresRlsTests` against a real server** (above). Highest-value follow-up.
2. **Platform RLS is still not enforced for the connecting role** — D2's policies lack
   `FORCE ROW LEVEL SECURITY`, so the owner bypasses them. Hardening it needs care: tenant
   seeding runs with `app.tenant_id` unset, so it would have to set the variable (or run as a
   role that is exempt) before FORCE can be turned on.
3. **PMO tables still have no RLS policy at all** (the other half of the D3 gap). B6 owns it.
4. **PMO should own its tables too**, mirroring §2 above; PMO entities are still in `/Shared`
   under `PlatformDbContext`.
5. **Legacy tables**: a dev database created before B5 still has the unused `Strategies`,
   `Perspectives`, `Objectives`, `KPIs`, `Initiatives` tables. Drop them, or drop and recreate
   the dev database — no data has ever been written to them.
6. **Audit actor is `"system"`** everywhere (pre-existing from B4). It needs the authenticated
   user, which means a current-user abstraction alongside `ITenantContext`.
7. **`PlatformDbContextModelSnapshot` is stale** — it predates D3 and does not include the PMO,
   lookup or audit entities, so `dotnet ef migrations add` against Platform would generate
   duplicates. SMO's snapshot is accurate; Platform's should be regenerated.
8. **Cause-effect links between objectives** (for F5's strategy map) and initiative↔delivery
   links are deliberately not here: X1 owns the links, F5 the canvas.
9. `Microsoft.AspNetCore.TestHost` drags in `System.Security.Cryptography.Xml` 9.0.0, which NuGet
   flags as a known vulnerability (NU1903) in both test projects.
10. **Local dev database credentials** are unknown to the repo. Now that the connection string is
    configuration-driven, put the working one in user secrets or `SMO_TEST_POSTGRES` rather than
    back into `appsettings.Development.json`.
