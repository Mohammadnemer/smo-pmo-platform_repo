# Session F3

## Session ID

F3

## Scope

A small shared component library (`Button`, `Card`, `Badge`), a light/dark
theme pair, and a per-tenant branding hook (logo mark/colour) — building on
F2's `AppShell` and CSS-custom-property token system rather than replacing
either.

## Done when

A tenant's branding applies without a code change.

## Prerequisites

- F2 (i18n & RTL shell) — the `--brand`/`--brand-soft`/`--brand-fg` tokens and
  `AppShell` it left in place are what this session makes tenant-configurable
  and theme-aware.

## Decisions made

- **Per-tenant branding is a data change, not a code change, today via a
  stubbed config map** (`shared/branding/branding.ts`), keyed by tenant id.
  There's no backend endpoint to fetch this from yet — **P4 ("Themes &
  branding admin")** is the not-yet-built session that gives tenant admins a
  real UI/API to manage logo, palette and favicon. Building that here would be
  building ahead of the roadmap (CLAUDE.md). The stub includes the seeded
  default tenant (matching `DefaultTenantId` in `appsettings.Development.json`)
  plus one extra demo tenant, so switching `tenantBrandings` config is
  provably enough to re-skin the whole shell (mark letter, brand colour,
  display name) with zero component edits.
- **Tenant resolution is a `?tenant=` query param for now**, not the real
  mechanism. The real one is the authenticated session's Entra `tid` claim,
  resolved server-side by B1's `TenantResolutionMiddleware` — that requires
  the real Entra tenant/app registration F1 already flagged as a follow-up.
  Until then, the query param is the only way to exercise per-tenant branding
  locally. `resolveTenantId()` documents this explicitly.
- **Branding applies via inline CSS custom properties on `<html>`**
  (`applyBranding` sets `--brand`/`--brand-soft`/`--brand-fg` via
  `style.setProperty`), which win over the stylesheet defaults in
  `index.css`. Those stylesheet defaults double as the fallback for an
  unrecognized tenant id and as what a fresh unbranded paint looks like before
  JS runs (they match the default-tenant stub exactly, so there's no flash).
- **Theme (light/dark) follows i18n's exact pattern from F2**: a
  `shared/theme/theme.ts` singleton applies `document.documentElement.dataset
  .theme` and persists to `localStorage` (`smo-pmo-theme`), defaulting to the
  OS's `prefers-color-scheme` when nothing is stored yet. A tiny
  `useTheme()` hook wraps it with `useSyncExternalStore` rather than adding a
  React Context provider — consistent with how `i18n.ts` is a plain
  side-effect singleton and `useTranslation()` (from the library) is the
  read/write hook.
- **Dark tokens are a second `:root[data-theme='dark']` block** in
  `index.css`, same property names as the light set — nothing that reads a
  `--text`/`--surface`/etc. token needs to know which theme is active.
  Semantic status tokens (`--ok`, `--warn`, `--risk`) got a `-soft` background
  pair added (used by `Badge`) since the light-theme `-soft` shades hard-coded
  into a component would otherwise be illegible on a dark surface.
  `--brand-soft` in dark mode is derived with `color-mix()` from the
  (tenant-specific) `--brand` rather than hard-coded, so it stays readable
  for *any* tenant colour, not just the default blue.
- **Component library is intentionally small**: `Button` (primary/secondary/
  ghost), `Card`/`CardHeader`/`CardBody`, and `Badge` (ok/warn/risk/neutral/
  brand tones, reusing the semantic tokens above). These are the primitives
  F4's scorecard (RAG badges), F6's project screens, and general admin forms
  will need first — not a speculative full kit. Applied immediately to the
  six page stubs (`Card` wrapping their placeholder body copy) and to
  `HomePage`'s API health line (`Badge`, ok/risk toned) so the library ships
  proven in real use rather than as unused scaffolding.
- Did **not** touch `AppShell`'s existing topbar/nav chrome buttons (sign-out,
  language switch, search) to route through the new `Button` component — those
  are pixel-tuned to the F2 design-prototype fidelity via dedicated
  `.app-shell__*` classes, and swapping them for a generic component risked
  regressing that fidelity for no material benefit. The one new control added
  to that chrome (the theme toggle) matches the existing icon-button pattern
  instead, consistent with how the language switch already looks.

## Addendum: workspace switcher + per-workspace left nav + route prefixes (pulled forward from F4–F6/F9)

Done in the same conversation immediately after F3 proper, at the user's
explicit direction (referencing the design prototype's PMO-workspace chrome
that F2 had deliberately deferred — see F2's decisions log). This is **not**
F3's own manifest scope; it's future sessions' navigation IA, built now on
top of F3's component library, with only F2/F3-level chrome — no real
scorecard, strategy map, PMO CRUD, or executive dashboard logic behind any of
it yet. Went through three corrections from the user before landing here:
Portfolios/Programs are peers of Projects, not children of it; the left nav
fully swaps per workspace rather than showing all workspaces flattened; and
routes are prefixed per workspace (`/smo/*`, `/pmo/*`, `/executive/*`,
`/settings/*`) with each workspace's overview mounted at `/<prefix>/home`.
What follows is the final state, not a pass-by-pass history.

### What changed

- Header workspace switcher pill (Strategy (SMO) / Projects (PMO) /
  Executive) from the design prototype, wired to real routes via `NavLink`.
  Its active state is computed from `matchWorkspace(pathname)` (matches the
  whole `/smo`, `/pmo`, `/executive` prefix), not `NavLink`'s own `isActive`
  — needed because the pill's `to` target is a specific sub-route
  (`/smo/home`) but must show active across every route under that prefix.
- The left nav is three sections:
  1. **Home** (`/`) — always visible, outside any workspace.
  2. **The active workspace's own peer list**, fully swapped based on the
     current route's prefix (`workspaceNavItems` in `AppShell.tsx`):
     - SMO (`/smo/*`): Home, Initiatives, Strategy map, Scorecard
     - PMO (`/pmo/*`): Home, Portfolios, Programs
     - Executive (`/executive/*`): Home (its only item)
     Each workspace's "Home" entry is that workspace's original overview
     page (`StrategyPage`/`ProjectsPage`/`ExecutivePage`), just relabeled
     and remounted at `/<prefix>/home` instead of keeping the domain name as
     both the route and the nav label. Visiting a route outside all three
     workspaces (global Home, or the `/settings/*` items) shows **no**
     workspace section — there's no "default" workspace.
  3. **Cross-cutting items** (`/settings/workflow`, `/settings/rollup`,
     `/settings/notifications`) — always visible, pinned to the bottom via
     `margin-block-start: auto`, matching the prototype's pinned "Admin"
     section placement.
- Bare `/smo`, `/pmo`, `/executive` each redirect (`<Navigate replace>`) to
  their `/home` sub-route, so typing the prefix alone still lands somewhere
  useful instead of falling through to the catch-all.
- Breadcrumb shows `Home > {label}`, where `{label}` is the workspace's own
  name (e.g. "Strategy (SMO)") when on that workspace's `/home` route —
  showing "Home > Home" there would be redundant — and the specific item's
  own label otherwise (e.g. "Home > Portfolios").
- Six new stub pages (same `Card`-wrapped placeholder pattern as the
  existing six): `ScorecardPage`, `StrategyMapPage`, `InitiativesPage`
  (`modules/smo/pages/`), `PortfoliosPage`, `ProgramsPage`
  (`modules/pmo/pages/`), `ExecutivePage` (`modules/rollup/pages/` — see
  below for why).
- `ExecutivePage` lives under `modules/rollup/pages/`, not a new `modules/
  executive/` folder — Executive isn't one of the six backend modules F1
  established folder-per-module for, and CLAUDE.md's Roll-up module
  description ("dashboards read the stored value") is the natural backend
  home for a future cross-module executive dashboard.
- Deliberately did **not** add Resources or Budget as PMO items — both are
  p2-phase in the manifest (B10/B11) and weren't part of what was asked;
  adding them would have been building further ahead of the roadmap than the
  explicit request called for.
- Five new icons in `icons.tsx` for the SMO/PMO peer items: `LayersIcon`
  (Portfolios), `ListIcon` (Programs — reuses the exact glyph the design
  prototype already drew for this), `GaugeIcon` (Scorecard), `MapIcon`
  (Strategy map), `FlagIcon` (Initiatives). `PresentationIcon` (Executive)
  was added earlier and is unchanged. Each workspace's "Home" row keeps its
  original domain-flavored icon (Target/Folder/Presentation) rather than
  reusing the global Home's grid icon three times over, for distinguishability.

### Correction: dropped literal "Home" labels, removed the global Home nav row

Immediately after the above, seeing it rendered surfaced two problems the
user flagged: (1) "Home" appeared four times in the left nav — once for the
app-level Home row, once per workspace's overview item — which read as
clutter rather than IA; (2) removing "Projects" as PMO's own label (in favor
of literally calling it "Home") lost a meaningful, recognizable tab name for
no real benefit.

Fix: each workspace's overview item (still mounted at `/<prefix>/home`,
content unchanged) is labeled with its **domain name** again — `nav.
strategyOverview` ("Strategy"), `nav.projectsOverview` ("Projects"), `nav.
executiveDashboard` ("Dashboard") — not `nav.workspaceHome` ("Home"), which
is now deleted. The standalone global "Home" row (routed at `/`, above the
workspace divider) is removed from the left nav entirely; the brand mark/
name in the top bar is now a link to `/` instead, giving the app-level Home
route a way back in without a dedicated nav row. The breadcrumb's special
"don't show 'Home > Home'" case was removed along with it — it's now a plain
`Home > {activeEntry.key}` for every route, no special-casing needed, since
no entry is ever literally labeled "Home" anymore. `.app-shell__nav-divider`
(only ever used to separate the removed Home row from the workspace items)
was deleted along with its CSS rule.

Verified: `npm run build` and `npm run lint` both clean after this change.
Same browser-verification gap as everything else in this addendum applies.
