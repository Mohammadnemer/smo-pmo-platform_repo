# Session B6

## Session ID

B6

## Scope

The PMO API & scheduler: CRUD for portfolios, programs, projects, tasks and dependencies,
RAID and status reports, plus the CPM (critical path method) engine wired server-side —
forward/backward pass, all four dependency types (FS/SS/FF/SF) with lead/lag, total float and
critical-path flagging, computed in calendar-aware working-day space and stored on each task.

## Done when

Saving a schedule and asking for its critical path returns the right tasks.

## Prerequisites

- B1–B5: request pipeline and tenant context, authentication, RBAC, mediator + audit
  interceptor, and the SMO API (as the template this session follows for module ownership,
  REST conventions and RLS).
- D1–D4: schema foundation, RLS, SMO/PMO tables, tenant seed.

## Decisions made

### 1. The PMO module now owns its entities and its tables

D3 had put the PMO entities in `/Shared` under `PlatformDbContext`, the same gap B5 closed for
SMO and explicitly left open for this session (B5 follow-ups #3 and #4). B6 makes the same
move:

- The entities live in `src/PMO/PmoEntities.cs` (namespace `SmoPmo.Pmo`).
- `PmoDbContext` maps them to `Pmo*`-prefixed tables and keeps its own migration ledger,
  `__EFMigrationsHistory_Pmo`, so PMO schema changes ship independently of Platform's and
  SMO's.
- The `AddSmoPmoSchema` Platform migration no longer creates the Portfolio/Program/Project/
  Task/Dependency/RAID tables; PMO's own initial migration does. Table names are prefixed
  (`PmoPortfolios`, `PmoTasks`, …) rather than reused, so an existing dev database does not
  collide — see *Follow-ups* for the leftover legacy tables, same as B5 left for SMO's.
- RLS (`ENABLE`/`FORCE ROW LEVEL SECURITY` + policy) is applied in PMO's own migration for all
  eight PMO tables. This closes the other half of the gap D3 left and B5 flagged directly for
  B6: "PMO tables still have no RLS policy at all."

### 2. The domain grew beyond the D3 stub to match the PRD and this session's own line

D3's Task/Dependency/RaidItem were placeholders (name/description only). To actually schedule
and compute a critical path, and to cover "RAID and status reports" from B6's own scope line,
the model grew to match PRD §6.2.2/§6.2.6/§6.2.7:

- **Project** gained `StartDate` (the CPM anchor) and `Status` (plain string, default
  `"Draft"`, following exactly the pattern B5 used for `Initiative.Status` — B7 owns the
  transitions, not this session).
- **TaskItem** gained `WbsCode`, `DurationDays`, `IsMilestone`, `PercentComplete`,
  `AssigneeUserId`, and the stored CPM output: `ScheduleStart`, `ScheduleFinish`,
  `TotalFloatDays`, `IsCritical`. The schedule fields are written only by `ScheduleQuery` —
  never accepted from a client — the same "stored, not recomputed on read" rule the roll-up
  engine follows (architecture-mvp.md §5); the difference is *when* it's computed (see #4).
- **Dependency** gained `LagDays` (lead/lag, PRD §6.2.2; may be negative for lead time).
- **RaidItem** gained `Severity`, `Status`, `OwnerUserId`, `DueDate`, and three nullable
  parent ids (`PortfolioId`/`ProgramId`/`ProjectId`) — RAID is present at all three levels
  (PRD §6.2.6) and exactly one parent must be set (`PmoValidation`).
- **StatusReport** is new: `ProjectId`/`ProgramId` (exactly one set), a reporting period,
  `OverallStatus` (a PMO-local RAG enum — modules don't share entity types, so this mirrors
  rather than reuses SMO's `RagStatus`), and free-text accomplishments/next-period/RAID/
  milestone fields. It is snapshot + history (PRD §6.2.7): create-only, no update or delete.
- Deliberately **not** added: WBS parent/child hierarchy and a separate `Effort` field
  (PRD lists both, but B11 — resource management, p2 — is the first session with a consumer
  for effort, and hierarchy has no consumer before F7's Gantt grid). Adding either now would
  be schema with no behaviour behind it.

### 3. A per-tenant working calendar was added — a non-negotiable this session could not defer

CLAUDE.md's non-negotiables require the Fri–Sat weekend to be per-tenant config that drives
schedule math, but no such config existed: D4's "Workday" lookups list all seven days and mark
none of them as weekend. B6 is the first session that does date math, so it could not defer
this to P3 (which owns the *admin UI* for editing tenant calendars) without breaking the
non-negotiable outright.

`PmoCalendar` is a new PMO-owned table, one row per tenant, with `WeekendDay1`/`WeekendDay2`
(default Friday/Saturday). It is auto-created with that default the first time a project's
schedule is computed — the same lazy-provision pattern D4 uses for tenant seeding — and P3
can let an admin edit it later without changing how the CPM engine reads it. This was a
judgment call rather than a listed open decision (architecture §12 does not mention calendar
ownership), so it is recorded here rather than as an ADR; `docs/decisions-open.md` is
unchanged.

### 4. The CPM engine is synchronous and eager, unlike the roll-up worker

Architecture §5 says roll-up is "debounced domain events in a background worker... dashboards
read the stored value." B6's schedule is *stored* the same way (never recomputed on read), but
computed *synchronously* on every write instead of debounced in the background:

- A project's task graph is small (this is CPM over one project, not a roll-up walk across the
  whole strategy graph), so there is no cost to justify deferring it.
- F7/F8 (Gantt rendering and drag-reschedule) need to see a save's effect immediately.

`ScheduleQuery.RecomputeAsync` reloads a project's tasks/dependencies, runs
`CriticalPathEngine.Compute`, and persists the result — called after every task write,
dependency delete, or a project start-date change. **Dependency create/update is the one case
that can turn a valid graph into an invalid one** (a cycle), so those two endpoints instead
build an in-memory candidate graph (existing dependencies + the new/edited one, not yet added
to the `DbContext`) and call `Compute` *before* writing anything. A `CyclicScheduleException`
there becomes a 400 with nothing persisted; only on success is the candidate added and
`ScheduleQuery.PersistAsync` called, so the new dependency and its schedule effect land in one
`SaveChangesAsync`. No database transaction is needed for this — the in-memory dry run is
what keeps invalid graphs out.

Deleting a task also deletes any dependency that referenced it before recomputing: the engine
has no duration to look up for a dependency pointing at a task that no longer exists, and
letting that reach `Compute` would throw on the very next recompute.

### 5. CPM works in integer working-day index space; only `WorkingCalendar` touches dates

Per architecture §7's layering, `CriticalPathEngine` (layer 3) never sees a `DateOnly` — tasks
are `(Id, DurationDays)`, dependencies are `(PredecessorId, SuccessorId, Type, LagDays)`, and
the forward/backward pass produces integer early/late start/finish indices and total float
using an **exclusive-end** convention (`EarlyFinish = EarlyStart + Duration`; a milestone's
`EarlyFinish == EarlyStart`). `WorkingCalendar` (layer 2) is the only place that converts an
index to a calendar date, skipping the tenant's weekend days. This split is what makes the CPM
math testable with plain GUIDs and integers (`CriticalPathEngineTests`) independently of any
database or calendar.

### 6. Routes and authorization follow B5's SMO conventions exactly

- REST resources under `/api/pmo/{portfolios|programs|projects|tasks|dependencies|raid|
  status-reports}`, flat with optional filter query params (`?projectId=`, …), plus two
  aggregate reads: `GET /projects/{id}/schedule` (the whole computed schedule + dependencies
  in one round trip) and `GET /projects/{id}/critical-path` (just the tasks with zero total
  float — the literal "ask for the critical path" from this session's acceptance line).
- `PmoPolicies.Read`/`Write` reuse B3's existing `"Project"` authorization resource, which
  already covered PM/Contributor/Admin read and PM/Admin write — the same way SMO's policies
  reuse the `"Strategy"` resource. The throwaway `GET /projects` demo endpoint from B3/B1 is
  removed now that the real surface exists, the same cleanup B5 did for `POST /strategies`.

## How it was verified

- `dotnet build SmoPmoPlatform.slnx` — succeeded, 0 warnings, 0 errors. Module boundaries still
  hold: PMO references only `/Shared`.
- `dotnet test tests/Pmo.Tests` — **20 passed, 0 failed, 2 skipped** (the skipped pair is the
  PostgreSQL suite, same situation as B5 — see below); `dotnet test tests/Platform.Tests` —
  **5 passed**; `dotnet test tests/Smo.Tests` — **24 passed, 0 failed, 2 skipped** (no
  regression from moving PMO's tables out of `PlatformDbContext`).
- **The acceptance line**, `ScheduleEndToEndTests.SavingAScheduleAndAskingForItsCriticalPathReturnsTheRightTasks`:
  builds a portfolio → program → project over HTTP, then three tasks (Design 5d, Procurement
  2d, Integrate 2d) with Design→Integrate and Procurement→Integrate FS dependencies —
  Procurement is the shorter parallel path. `GET .../critical-path` returns exactly Design and
  Integrate (not Procurement), each with zero float and `IsCritical = true`. Because the
  project starts on a known Monday (2024-01-01), the test also asserts calendar-aware dates
  by hand: Design runs Mon–Sun (5 working days, spanning the Fri/Sat weekend) and Integrate
  starts the following Monday — proving the working-calendar layer, not just the graph math.
  `GET .../schedule` is checked against the same fixture and additionally confirms
  Procurement's 3 days of float.
- **CPM correctness in isolation** (`CriticalPathEngineTests`, no database): linear chain
  (all critical, zero float), a shorter parallel path (positive float, not critical), each of
  FS/SS/FF/SF with the textbook constraint, FS with lag, a zero-duration milestone, a cyclic
  graph (rejected via `CyclicScheduleException`), a dependency referencing an unknown task
  (rejected via `UnknownScheduleTaskException`), an empty project, and `WorkingCalendar`'s
  weekend skipping / forward-rolling in both directions.
- **Cycle rejection over HTTP**: `ADependencyThatWouldCreateACycleIsRejectedAndNothingIsWritten`
  — B depends on A, then A→B is attempted; 400, and the dependency list still has exactly one
  row (proving nothing was written, not just that the response was an error).
- **Task deletion hygiene**: deleting a task also removes dependencies that referenced it and
  reschedules the remaining task back to the project start.
- **Validation**: a milestone with nonzero duration and a non-milestone with zero duration are
  both rejected.
- Tenant isolation and RBAC at the API layer (`PmoAccessTests`): tenant B cannot list, fetch,
  or hang a program off tenant A's portfolio; a Contributor can read but not write or delete;
  an unauthenticated caller is 401.

### Not verified — live PostgreSQL

Same situation B5 documented and did not resolve: the local PostgreSQL server rejects the
`postgres/postgres` credentials the repo assumes. `PostgresRlsTests` (migration, RLS,
`FORCE ROW LEVEL SECURITY`, Npgsql translation of the schedule queries) is marked `Skip` for
the same reason B5's was — a silently-passing test that never ran would be worse than an
explicit skip. To close this out: set `PMO_TEST_POSTGRES` to a working connection string and
delete the two `Skip` arguments in `tests/Pmo.Tests/PostgresRlsTests.cs`.

## Follow-ups

1. **Run `PostgresRlsTests` against a real server** (above) — still the highest-value
   follow-up across B5 and B6 both.
2. **Legacy tables**: a dev database created before B6 still has the unused `Portfolios`,
   `Programs`, `Projects`, `Tasks`, `Dependencies`, `RAID` tables from the old D3 migration.
   Drop them, or drop and recreate the dev database — same situation B5 left for the SMO
   legacy tables.
3. **`PmoCalendar` has no admin surface yet** — P3 owns letting a tenant admin edit the
   weekend days (and add holidays, which `WorkingCalendar` does not model at all yet).
4. **Cross-project moves are a known gap**: editing a dependency or task's `ProjectId` to a
   *different* project only recomputes the new project's schedule, not the one it left. This
   is not exercised by any current UI (F6/F7 don't offer moving a task between projects) and
   was left rather than building dual-project recompute for an unused path.
5. **WBS hierarchy and per-task `Effort`** are deliberately not modelled (see decision #2) —
   pick these up when F7's Gantt grid or B11's resource management actually need them.
6. **Program/portfolio-level Gantt roll-up** (PRD §6.2.4/§6.2.3 — "program-level Gantt rolled
   up from child projects") is out of scope: B6's CPM is per-project only.
7. `PlatformDbContextModelSnapshot` remains stale from before D3 (B5 follow-up #7, still
   unaddressed) — it never included PMO's entities either, so removing them from
   `PlatformDbContext` required no snapshot change and the discrepancy is unchanged by this
   session.
