# Session F5

## Session ID

F5

## Scope

A React Flow (`@xyflow/react`) canvas at `/smo/map`: objectives laid out by perspective
(rows), cause-effect arrows between them, RAG colour, and drill-down into a clicked
objective's KPIs and initiatives — replacing the F1/F3-era stub page.

Cause-effect links between objectives are real domain data (PRD §6.1.1, §6.1.6:
"Objective — … with cause-effect links to other objectives (this produces the strategy
map)"), and nothing before this session created that data — D3/B5 shipped Strategy →
Perspective → Objective → KPI → Initiative but no link between objectives. Building the map
therefore needed a small SMO-module backend slice first: an `ObjectiveLink` entity/table/
migration/endpoints, and the edges added to the scorecard aggregate.

## Done when

Clicking an objective drills into its KPIs and initiatives.

## Prerequisites

- B5 (SMO API) — the scorecard aggregate and `ScorecardQuery` this session extends.
- F4 (Scorecard) — `useScorecardQuery`/`useStrategiesQuery`, the dev auth bypass and demo
  seed this page reuses, and the RAG-tone mapping factored out of it this session (see
  Decisions made).

## Decisions made

- **Cause-effect links are a new SMO-owned entity (`ObjectiveLink`), not a frontend-only
  construct.** The PRD is explicit that these are domain data used to CRUD objectives and
  produce the map, not something a page can synthesize from the tree it already has (there
  is no derivable "this objective causes that one" from perspective/display order alone).
  Added: `ObjectiveLink : BaseEntity` (`SourceObjectiveId`, `TargetObjectiveId`, `Note`) in
  `SmoEntities.cs`; table `SmoObjectiveLinks` in `SmoDbContext.cs` with **both** FKs to
  `Objective` as `DeleteBehavior.Restrict` (Postgres rejects two `Cascade` paths into the
  same table from the same origin table); a hand-written migration
  (`20260908120000_AddObjectiveLinks.cs`, RLS `FORCE`d from creation, matching
  `InitialSmoSchema`'s reasoning — a table this session exposes over HTTP does not ship
  without tenant isolation even briefly); `ObjectiveLinkWriteModel`/`ObjectiveLinkResponse`;
  thin CRUD (`GET /api/smo/objective-links?objectiveId=|strategyId=`, `POST`, `DELETE` — no
  `PUT`, an edge has no fields worth updating beyond existing or not) in `SmoEndpoints.cs`;
  validation rejecting a self-link in `SmoValidation.cs`.
- **The scorecard aggregate grew an `ObjectiveLinks` field rather than a second round trip.**
  Consistent with ADR 0002 (the whole scorecard in one call) and with what F4 already
  established as the pattern F5 would need. `ScorecardQuery.BuildAsync` fetches links scoped
  to the objective ids already loaded for the response, so **a link into a hidden perspective
  never appears** — the same `includeHidden` boundary the rest of the aggregate respects.
- **Demo seed now includes 7 cause-effect edges** (`SmoDemoSeed.cs`), following the classic
  Kaplan/Norton bottom-up BSC chain (Learning & Growth → Internal Process → Customer →
  Financial) already implied by the seeded perspective order; every seeded objective carries
  at least one edge so the map has no isolated nodes. Seeded by objective name via a
  `Dictionary<string, Guid>` built during the existing seed loop — no second read.
- **Node colour is the real stored roll-up (`objective.Health`), not a client-side
  approximation — same call F4 made for the scorecard's objective/strategy badges, applied
  here identically.** Since X2 (roll-up worker) doesn't exist yet, every node currently
  renders with a neutral border. Rather than fabricate a colour from the KPI mix to make the
  demo look busier, each node also carries the real `RagSummary` (KPI RAG counts) — the same
  honest, already-computed data F4 shows on scorecard cards, extracted into a shared
  `smo/RagSummary.tsx` + `smo/rag.ts` (F4's own follow-up note: "if that duplication becomes
  real … extract a shared `smo/rag.ts` then" — it did, so `ScorecardPage.tsx` now imports the
  same helpers instead of keeping its own copy).
- **Drill-down is an in-place side drawer, not a page navigation.** Clicking an objective
  node opens a `Card` beside the canvas showing its target state, RAG mix, a compact KPI
  list (name / actual / target / RAG) and an initiative list (name / sponsor / status) —
  literally "drills into" without leaving the map, closes on an `×` button or a canvas-pane
  click.
- **No auto-layout library (dagre/elkjs).** Rows = perspectives in display order (Financial
  at top, matching the conventional BSC map); objectives within a row are evenly spaced from
  a fixed label gutter. The demo tree is small and regular; CLAUDE.md's "keep MVP lean"
  applies to a graph-layout dependency as much as to infrastructure. Flagged as a real
  follow-up for a tenant with a much larger, irregular objective tree.
- **RTL mirroring is done once, in the layout math, not via CSS.** The canvas `<div>` is
  forced `dir="ltr"` (React Flow lays out nodes by raw x/y and isn't RTL-aware); under RTL
  every node's `[start, start+width)` span is mirrored across `x=0` — not just its start
  x — so the gap on both sides of the fixed label gutter stays equal. **Found and fixed a
  real bug here during verification**: an earlier version negated only the start x, which
  left each RTL node's *right* edge swinging back past `x=0` on top of the label column,
  invisibly overlapping it (see How it was verified). Also **found and fixed** that
  `fitView` only computes its pan/zoom once on mount and does not re-run when `nodes`
  changes — so a language toggle (which recomputes every node's mirrored x) left the canvas
  showing the *old* language's transform against the *new* positions. Fixed by `key=
  {language}` on `<ReactFlow>`, forcing a clean remount (and so a fresh `fitView`) each
  toggle.

## How it was verified

- `dotnet build src/Api/Api.csproj` — clean.
- `dotnet test tests/Smo.Tests` — **27 passed, 0 failed, 2 skipped** (the same pre-existing
  PostgreSQL-only skips as F4) — includes the 3 new `ObjectiveLinkTests`.
- `npm run build` (`tsc -b && vite build`) and `npm run lint` (oxlint) — both clean.
- **Ran the real stack against a live local PostgreSQL** (the machine's own
  `postgresql-x64-18` service, not a mock): started `src/Api` in `Development`, confirmed the
  new `AddObjectiveLinks` migration applied cleanly alongside the existing ones, deleted the
  stale pre-F5 demo strategy so the (idempotent, seed-once) `SmoDemoSeed` would re-run, and
  confirmed via `curl` that the scorecard aggregate returns 4 perspectives / 8 objectives /
  **7 `objectiveLinks`** with the intended source→target pairs.
- **Ran the real app in a headless browser** (Playwright driving the system's installed
  Chrome via `playwright-core`, since no project skill or `chromium-cli` was available —
  recommending `/run-skill-generator` to capture this for next time, as F4 also noted) against
  the Vite dev server proxying to the live API. This is where the two real bugs under
  "Decisions made" were actually caught — not by build/lint/unit tests, which were clean at
  every step:
  - First pass: the canvas rendered completely blank (a real, in-browser rendering bug, not
    a test-tooling artifact) — `@xyflow/react`'s root div computes `height: 100%`, which
    doesn't resolve against an ancestor whose own height comes only from `min-height` on an
    otherwise `height: auto` chain (the card wrapping the canvas is sized by content).
    Fixed by giving `.strategy-map-page__canvas` a definite `height: 640px` instead of
    `height: 100%; min-height: 640px`.
  - After that fix: LTR rendered correctly (8 nodes, 4 row labels, 7 edges, click → drawer
    with the right KPIs/initiatives, zero console errors) but Arabic mode showed several
    objective nodes and perspective labels clipped/overlapping. Root-caused by inspecting
    live DOM rects (`getBoundingClientRect()` on the actual page, not assumption) down to the
    exact pixel overlap, which is what surfaced the two RTL bugs fixed above (mirroring only
    a node's start x, and `fitView` not re-running on a language toggle). Re-verified after
    each fix until LTR and RTL screenshots matched cleanly, click-to-drawer worked in both,
    and `console --errors`-equivalent output was empty in both.
  - Screenshots taken of all four states (LTR map, LTR drawer open, RTL map, RTL drawer
    open); drawer text confirmed correct in both languages (e.g. "Increase recurring
    revenue" / "زيادة الإيرادات المتكررة" with matching KPI figures and the seeded
    initiative).

## Follow-ups

- No auto-layout library is used (see Decisions made) — revisit with dagre/elkjs if a real
  tenant's objective tree turns out large or irregular enough that even column spacing looks
  wrong.
- Node colour shows the real (currently all-`NotSet`) stored roll-up health rather than a
  fabricated one — once X2 (roll-up worker) lands and starts writing `Objective.Health`, the
  map should start showing real colour variation with no code change needed here, only data.
- Objective-link CRUD exists on the API (`POST`/`DELETE /api/smo/objective-links`) but there
  is no admin UI to create/edit links yet — PRD §6.1.1 frames this as part of objective CRUD,
  which doesn't have a UI at all yet either; tracked for whichever future session adds
  objective editing.
- `DevAuthenticationHandler`/`SmoDemoSeed` remain temporary, load-bearing only for local dev
  (same F4 follow-up, unchanged by this session).
- Visual verification covered a 1400×900 desktop viewport in both languages; narrow-viewport
  behaviour for the canvas + drawer side-by-side layout is untested (the drawer likely needs
  to stack below the canvas rather than beside it below some width — not addressed here).
