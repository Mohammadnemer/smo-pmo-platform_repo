# Session X1

## Session ID

X1

## Scope

Track X · Integration & roll-up — "Initiative ↔ delivery links". M:N links from SMO
initiatives to PMO programs/projects, each with a `primary` flag and a
`contribution_weight`, per architecture-mvp.md §5 and PRD §5.3's contribution model.

This is the first cross-module feature in the platform: Roll-up owns the link table but,
per the module boundary (architecture-mvp.md §9), must never project-reference SMO or PMO
to validate an id or read a display name. That gap is closed with a new cross-module
read seam in `/Shared` (see "Decisions made").

## Done when

An initiative lists the programs and projects delivering it. Verified live against
PostgreSQL: `GET /api/rollup/initiatives/{id}/delivery` for the seeded "Unified Platform
Rollout" initiative returns its primary program (Core Platform Program, 70%) and secondary
project (Tenant Onboarding Revamp, 30%), resolved through the mediator rather than a
cross-module table join.

## Prerequisites

- B5 (SMO API — initiatives) and B6 (PMO API — programs/projects) for the entities being
  linked.
- T1 (module skeletons) for the Rollup module stub this session fills in.

## Decisions made

- **Cross-module reads go through new query contracts in `/Shared`**
  (`src/Shared/Integration/CrossModuleQueries.cs`): `GetInitiativeSummaryQuery`,
  `GetProgramSummaryQuery`, `GetProjectSummaryQuery`, each an `ICommand<TResult>` returning
  a small summary record (id + display name). The *contract* lives in `/Shared` because
  every module already depends on it; the *handler* stays owned by whichever module holds
  the table — `InitiativeSummaryQueryHandler` in SMO, `ProgramSummaryQueryHandler` /
  `ProjectSummaryQueryHandler` in PMO. Roll-up calls these through `IMessageBus` both to
  validate the ids on a write and to resolve names for the aggregate read. This was the
  first real exercise of the "commands + domain events, never a direct call" rule
  (architecture-mvp.md §9) for a *read*, not just a write — the pattern the roll-up worker
  (X2) will reuse to walk `project → initiative → objective → strategy`.
- **The link is a bare-id table, not an EF-navigable one.** `InitiativeDeliveryLink` has
  plain `Guid`/`Guid?` columns (`InitiativeId`, `ProgramId`, `ProjectId`) with no
  `HasOne(...)` — there is nothing to navigate to in another module's `DbSet`.
- **Exactly one of `ProgramId`/`ProjectId`**, validated the same way PMO's `RaidItem`
  validates "exactly one of three parents" (count non-null, reject unless it's 1).
- **At most one primary link per initiative**, enforced in the endpoint (checked on both
  POST and PUT, excluding self on PUT) — not a DB constraint, matching how B5/B6 validate
  parent references at the application tier rather than in schema.
- **New `Rollup` RBAC resource** rather than reusing `Strategy` or `Project`: linking spans
  both domains, so `Admin`/`StrategyOwner`/`PM` can write, with the broader read set
  (`Contributor`, `KpiOwner`, `Executive`, any org-unit member) mirroring Strategy/Project
  reads.
- **Dev seed lives in `/Api`, not a `RollupDemoSeed` inside `/Rollup`.** Matching seeded
  rows by name needs `SmoDbContext` and `PmoDbContext` in scope together, and only the
  composition root may hold all three contexts — a module seed class would violate its own
  boundary.
- No frontend session in the manifest yet consumes this (no F-track row references
  "delivery links"), so this session stayed backend + tests, per CLAUDE.md's "build the
  named session, then stop."

## How it was verified

- `dotnet build SmoPmoPlatform.slnx` — clean build; `Directory.Build.targets`'
  `EnforceModuleBoundaries` target passed, confirming Rollup still project-references only
  `/Shared` despite the new cross-module calls.
- `dotnet test` on `Rollup.Tests` (7/7 passing) covers: the aggregate read returning both a
  primary program and a secondary project with correct weights (the "Done when" line
  itself); exactly-one-of-program-or-project validation; rejecting unknown
  initiative/program/project ids (the cross-module existence check); at-most-one-primary
  enforcement; RBAC (reader can read, cannot write); anonymous 401; and tenant isolation
  (tenant B cannot see, fetch, or hijack tenant A's link or initiative).
- Re-ran `Smo.Tests` (24 passed / 2 skipped), `Pmo.Tests` (27 passed / 2 skipped),
  `Platform.Tests` (5 passed) — no regressions from the new SMO/PMO query handlers.
- Ran the API live against a real local PostgreSQL server (`dotnet run`, Development
  environment): the Rollup migration applied (`RollupInitiativeLinks` table + RLS policy),
  the dev seed created 3 links, and
  `GET /api/rollup/initiatives/{unified-platform-rollout-id}/delivery` returned the primary
  program and secondary project with names resolved live through the mediator — the exact
  scenario the "Done when" line describes, not just an in-memory test double.
