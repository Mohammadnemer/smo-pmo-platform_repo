# Session F6

## Session ID

F6

## Scope

Portfolio/program/project lists, a project workspace shell and RAID panels — the real PMO
screens, consuming B6's existing PMO API (`/api/pmo/*`: portfolios, programs, projects, the
CPM-computed schedule aggregate, and RAID) live, replacing the F3-era stub pages.

## Done when

A project workspace opens with its schedule and RAID.

## Prerequisites

- B6 (PMO API) — portfolios/programs/projects/tasks/dependencies/RAID CRUD, the CPM engine
  wired server-side, and the `GET /projects/{id}/schedule` aggregate this session reads.
- F3 (design system) — `Card`/`Badge` components and CSS tokens this page's tables and
  status/severity colouring build on.
- F4 (dev auth bypass + demo-seed pattern) — reused as-is; no changes needed to
  `DevAuthenticationHandler` or the vite proxy.

## Decisions made

- **A dev-only demo portfolio/program/project tree is seeded at API startup**
  (`src/PMO/PmoDemoSeed.cs`, called from `Program.cs` behind the same `IsDevelopment()` check
  F4 used for SMO), because B6 never seeded PMO data. Two portfolios → three programs → four
  projects; the flagship project (`Tenant Onboarding Revamp`) gets a real diamond-shaped
  task/dependency network (API branch 10 days, UI branch 7 days) so the CPM engine actually
  produces a partial critical path to look at, instead of every task trivially being
  critical the way a single chain would be — verified live: `Build Onboarding API` and
  everything else on the long path came back `isCritical: true`, `Build Onboarding UI` came
  back `isCritical: false` with `totalFloatDays: 3`. RAID items are spread across all four
  categories and severities on that same project. Idempotent (skips if a portfolio already
  exists for the tenant).
- **Found and fixed a real FK-ordering bug while building the seed.** `RaidItem`'s
  `PortfolioId`/`ProgramId`/`ProjectId` are bare `Guid?` columns with no `HasOne(...)`
  configured in `PmoDbContext` (deliberate — exactly one of three optional parents, not a
  single navigable relationship), so EF Core's change tracker has no dependency edge telling
  it to insert the parent row first. A single `SaveChangesAsync` covering both the
  portfolios/programs/projects/tasks/dependencies *and* the RAID items intermittently batched
  the RAID insert ahead of its parent and hit `FK_PmoRaidItems_PmoProjects_ProjectId` (caught
  live when first running the seed against real PostgreSQL). Fixed by an explicit
  `SaveChangesAsync` after the parent tree is added, before adding any `RaidItem`.
- **The schedule panel is read-only.** It renders the CPM-computed schedule aggregate
  (WBS, duration, % complete, start/finish, float, critical-path badge) but has no task
  create/edit/drag UI — authoring the task graph is F7/F8's Gantt, and building a second,
  throwaway task-entry form here would be scope creep this session doesn't need. The empty
  state says so explicitly (mirrors F4's "roll-up not yet computed" honesty) rather than
  silently showing a blank table.
- **RAID and the three parent-entity lists (Portfolio/Program/Project) do get real create
  forms**, unlike the read-only schedule — there's no other way to populate a portfolio/
  program/project/RAID item at all otherwise (B7's workflow doesn't own creation, just
  transitions), and PMO's PRD framing treats these as basic CRUD screens, not something a
  future session owns. Edit/delete are deliberately left out (`PUT`/`DELETE` already exist
  server-side for whichever session wires them up) — out of scope for "lists ... and RAID
  panels."
- **Filtering is via URL search params, not local component state** (`?portfolioId=`,
  `?programId=`), so a portfolio/program row's "view children" link is a plain, bookmarkable
  `<Link>` rather than requiring the list page to already be mounted. `usePortfoliosQuery`/
  `useProgramsQuery`/`useProjectsQuery` all support an *unfiltered* fetch (param omitted) as
  well as a filtered one, reused to compute per-row child counts (e.g. a portfolio row's
  "Programs" count) without a second bespoke endpoint.
- **No `localized()` bilingual field handling on PMO data.** Unlike SMO's entities
  (`Name`/`NameAr`), PMO's `Portfolio`/`Program`/`Project`/`RaidItem` contracts have no Arabic
  twin field at all (`PmoContracts.cs`) — so every English string just renders as-is under
  Arabic, same as `Initiative.Status` already does on the Scorecard page. RTL mirroring
  itself (nav, breadcrumb order, table column order) comes for free from logical CSS
  properties and default flex-row reversal — no PMO-specific RTL code was needed, and this
  was confirmed visually (see verification).
- **Project.Status stays a free string** (`PmoEntities.cs`'s own comment: "B7's fixed flow
  owns the transitions"). The create form offers a fixed dropdown (`Draft`/`Active`/
  `OnHold`/`Completed`/`Cancelled`) purely as a UI convenience — the API validates only
  `Name`/`ProgramId`, so this is not a contract and B7 can redefine the vocabulary freely.
- **RAID severity/category badge tones and translated labels are static lookup maps**
  (`SEVERITY_TONE`, `CATEGORY_KEY`, `SEVERITY_KEY` in `ProjectWorkspacePage.tsx`), matching
  `ScorecardPage.tsx`'s `RAG_TONE`/`RAG_KEY` convention, rather than dynamic `t(`pages....${x}`)`
  interpolation — keeps i18n keys grep-able and matches the one existing precedent in this
  codebase.

## How it was verified

- `dotnet build src/Api/Api.csproj` — clean.
- `dotnet test tests/Pmo.Tests` — **20 passed, 0 failed, 2 skipped** (pre-existing
  PostgreSQL-only skips, unrelated to this session).
- `npm run build` (`tsc -b && vite build`) and `npm run lint` (oxlint) — both clean.
- **Ran the real stack end to end against a live local PostgreSQL** (not mocked): confirmed
  via `curl` that `/api/pmo/portfolios`, `/api/pmo/projects/{id}/schedule` and
  `/api/pmo/raid?projectId=` return the seeded demo tree with the intended CPM shape
  (`Build Onboarding API` critical with 0 float, `Build Onboarding UI` non-critical with 3
  days float, project finish `2026-02-11`) and the 4-item RAID spread.
- **Ran the real app in a headless browser** (Playwright against the already-cached system
  Chromium): loaded `/pmo/home`, `/pmo/portfolios`, `/pmo/programs`, clicked a project row
  from the list into `/pmo/projects/{id}`, and confirmed the workspace renders the breadcrumb
  (Portfolio / Program), status badge, the 6-row schedule table with the critical-path rows
  highlighted, and the 4-row RAID table — zero console/page errors. Switched to Arabic on the
  workspace page and confirmed `dir="rtl"`, mirrored breadcrumb/table order, and translated
  RAID category/severity labels, matching the light theme. Screenshots taken of all of the
  above.
- **Exercised the create forms live**, not just read paths: submitted the RAID "Add RAID
  item" form and the Portfolios "New portfolio" form through the running app and confirmed
  each new row appeared in its table without a page reload (React Query cache invalidation
  working), then deleted both test rows via the existing `DELETE` endpoints to leave the demo
  seed clean.
- While first running the seed against real PostgreSQL, it threw
  `FK_PmoRaidItems_PmoProjects_ProjectId` — see "Decisions made" above; fixed and re-verified
  clean on a second run (idempotency check also re-confirmed: seed no-ops on an already-seeded
  tenant).
