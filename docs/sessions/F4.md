# Session F4

## Session ID

F4

## Scope

A scorecard table with RAG, objective and KPI detail, and trend charts, consuming B5's
existing SMO scorecard aggregate (`GET /api/smo/strategies/{id}/scorecard`) live from the
API — replacing the F3-era stub page.

## Done when

A RAG scorecard renders live from the SMO API.

## Prerequisites

- B5 (SMO API) — the scorecard aggregate this page reads, and its KPI RAG evaluation.
- F3 (design system) — `Card`/`Badge` components and CSS tokens (`--ok`/`--warn`/`--risk`)
  this page's RAG colouring builds on.

## Decisions made

- **A dev-only auth bypass was required before anything could render live, and this was
  flagged to the user rather than silently built.** F1/F2 already deferred the real Entra
  External ID tenant/app registration; without it `src/Api`'s JwtBearer scheme 401s every
  call, including from the SPA. The user chose "add a dev-only fake auth scheme" (over
  "verify via tests only" or "wire real Entra first"). `src/Api/Auth/
  DevAuthenticationHandler.cs` mirrors `tests/Smo.Tests/SmoTestHost.cs`'s
  `TestAuthenticationHandler` (same claim shape, same header-override pattern via
  `X-Dev-Tenant`/`X-Dev-Roles`) but always succeeds with a fixed identity (tenant =
  `DefaultTenantId`, role `Admin`) when no override header is sent — so a plain SPA
  `fetch()` with no custom headers just works. `AuthenticationExtensions.AddApiAuthentication`
  now takes `IHostEnvironment` and only makes `DevAuth` the default scheme when
  `environment.IsDevelopment()`; the real `JwtBearer` scheme is registered unconditionally
  and untouched. `ASPNETCORE_ENVIRONMENT` defaults to `Production` when unset, so this can't
  activate by omission in a real deployment.
- **A dev-only demo scorecard tree is seeded at API startup** (`src/SMO/SmoDemoSeed.cs`,
  called from `Program.cs` behind the same `IsDevelopment()` check), because B5 never
  seeded SMO data — only `PlatformDbContext.SeedTenantAsync`'s tenant/lookup rows exist out
  of the box. It's a full Strategy → 4 Perspectives → 8 Objectives → 12 KPIs (with 6 months
  of trend measurements each) → 4 Initiatives tree, deliberately spread across RAG bands
  (4 green / 4 amber / 3 red / 1 not-set) so the page has something worth rendering rather
  than an empty or all-green scorecard. Idempotent (skips if a Strategy already exists for
  the tenant). SMO's tables `FORCE ROW LEVEL SECURITY`, so the seeder sets the scope's
  `ITenantContext.TenantId` before touching `SmoDbContext` — without that the insert is
  silently blocked by the same RLS policy that protects real tenant data, the same
  mechanism B5's audit trail relies on (`AuditingSaveChangesInterceptor` stamps
  `TenantId`/`CreatedAt`/`CreatedBy` from that same context, so the seed doesn't set them by
  hand).
- **Found and fixed a proxy/route-prefix mismatch that would have 404'd every SMO call.**
  `web/vite.config.ts`'s dev proxy stripped the leading `/api` before forwarding to the
  backend — correct for `/health` (mapped at the backend's root), but `SmoEndpoints` maps
  its whole surface under `/api/smo/*` per ADR 0002, so the stripped path never matched.
  This had never been exercised before: `useHealthQuery` (F1) is the only prior consumer,
  and it happens to work under the old stripping. Fixed by making the proxy a pure
  path-preserving passthrough (matches how a real gateway would route `/api/*` to the API
  container in production — T2/T3, not yet built), and adding `app.MapGet("/api/health",
  …)` alongside the existing root `/health` so the SPA's existing health check keeps
  working the same way through the same proxy rule.
- **No charting library was added.** Following the same "built from scratch" spirit as the
  Gantt (a locked decision) and the "keep MVP lean" guidance, the KPI trend is a small
  inline-SVG `Sparkline` (`web/src/shared/ui/Sparkline.tsx`) — a polyline plus an end-point
  dot, no dependency. It mirrors under RTL via `transform: scaleX(-1)` scoped to `:root[dir=
  'rtl']` so a trend's oldest→newest reading order still reads start-to-end regardless of
  direction (verified in the Arabic screenshot below).
- **RAG/roll-up split, rendered honestly.** Per-KPI RAG (`KpiEvaluation`, computed on read)
  drives each KPI row's badge and its sparkline's colour. Objective/perspective/strategy
  roll-up `Health` is a *stored* value only X2 (not yet built) ever writes — CLAUDE.md's
  roll-up non-negotiable says dashboards must never recompute it on read — so this page
  does not fabricate an objective/strategy RAG badge from KPI counts. Instead it shows the
  aggregate `RagCounts` (e.g. "1 Green · 1 Amber") the scorecard aggregate already returns
  at every level, which is real, already-computed data rather than a client-side
  approximation of a value that has a real, different meaning once X2 exists.
- **Bilingual field selection is a new small shared helper**
  (`web/src/shared/i18n/localized.ts`), not per-component logic: `localized(en, ar,
  language)` returns the Arabic twin only when the current language is Arabic *and* a
  translation exists, falling back to English otherwise (not every seeded row has bothered
  filling in every `…Ar` column). `Vision`/`Mission` have no `…Ar` field in
  `StrategyResponse` at all (unlike `Name`/`Description`), so those are shown as-is with no
  language branching — a deliberate difference from `Name`, not an oversight.
- **RagStatus/KpiDirection/KpiFrequency arrive as raw numbers on the wire.** No
  `JsonStringEnumConverter` is registered anywhere in `src/Api`, and adding one now would be
  a global change affecting B5's existing contracts/tests for a single new consumer — out of
  scope for this session. `web/src/modules/smo/api/scorecardTypes.ts` documents the
  numeric mapping in a comment and types each enum as its literal union (e.g. `RagStatus =
  0 | 1 | 2 | 3`) rather than guessing at string values.
- **One strategy, picked implicitly.** The scorecard page calls `GET /api/smo/strategies`,
  takes the first result, and feeds its id into the scorecard aggregate query — there is no
  strategy picker UI. This matches the PRD's "Strategy — root per org unit" framing (single
  strategy is the common case) and the demo seed only ever creates one; a picker is out of
  scope until multi-strategy tenants are an actual requirement.

## How it was verified

- `dotnet build src/Api/Api.csproj` — clean.
- `dotnet test tests/Smo.Tests` — **24 passed, 0 failed, 2 skipped** (pre-existing
  PostgreSQL-only skips, unrelated to this session) — confirms the auth signature change
  didn't regress B5's suite.
- `npm run build` (`tsc -b && vite build`) and `npm run lint` (oxlint) — both clean.
- **Ran the real stack end to end against a live local PostgreSQL** (not mocked): `dotnet
  run` from `src/Api` against `Host=localhost;Database=smo_pmo_platform`, confirmed via
  `curl` that `/api/smo/strategies` and the scorecard aggregate return the seeded demo tree
  with no bearer token (dev bypass working) and the intended RAG spread — `{green:4,
  amber:4, red:3, notSet:1}` at the strategy level, matching per-KPI achievement math
  exactly (e.g. Gross Margin 38/55 = 69.09% → Red; ARR Growth 19.4/20 = 97% → Green).
- **Ran the real app in a headless browser** (Playwright against system Chrome, since no
  project skill or `chromium-cli` was available — recommending `/run-skill-generator` to
  capture this for next time) at `http://localhost:5173/smo/scorecard` with `web/.env.local`'s
  existing `VITE_SKIP_AUTH=true`: confirmed the strategy name, all 4 perspectives, RAG badge
  mix, and sparklines render from live data; switched language to Arabic via the top bar and
  confirmed full RTL mirroring (nav, table column order, sparkline direction) plus Arabic
  strategy/perspective/objective/KPI names; zero browser console errors in either state.
  Screenshots taken of both.

## Follow-ups

- F5 (Strategy map) will want the same `useScorecardQuery`/RAG-tone mapping — if that
  duplication becomes real (not just two similar switch statements), extract a shared
  `smo/rag.ts` then, not preemptively now.
- Once X2 (roll-up worker) exists and starts writing `Health`/`HealthScore` on
  objectives/strategy, this page should grow a real roll-up RAG badge at those levels
  alongside the KPI `RagCounts` it already shows — tracked here so it isn't forgotten.
- `DevAuthenticationHandler`/`SmoDemoSeed` are both meant to be temporary: once F1's real
  Entra tenant/app registration follow-up lands, `AddApiAuthentication`'s `useDevAuth`
  branch (and the seed call) should be revisited — probably kept for local dev convenience
  but no longer load-bearing for "does the scorecard render."
- The `vite.config.ts` proxy fix (passthrough instead of stripping `/api`) needs re-checking
  once T2/T3 (real hosting) exist, to confirm the real gateway's routing shape actually
  matches what dev now assumes.
- No strategy-picker UI exists yet (first strategy is implicit) — revisit once a tenant with
  more than one strategy is a real scenario.
- Visual verification covered the two states above; it did not check narrow-viewport/mobile
  layout for the KPI table (it has `overflow-x: auto` as a safety net, untested).
