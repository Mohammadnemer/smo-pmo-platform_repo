## Scope

Gantt rendering: a virtualised grid (left) + SVG timeline (right) over B6's CPM-computed
schedule aggregate (`GET /pmo/projects/{id}/schedule`) — bars, dependency arrows, critical-path
highlight, today line, RTL. Replaces the plain read-only schedule table F6 shipped as a
placeholder. This is architecture-mvp.md §7's layer 4 ("rendering"); authoring/dragging/
rescheduling stays out of scope for F8.

## Decisions made

- **No virtualization library.** Row windowing (visible range + `OVERSCAN_ROWS` overscan,
  recomputed from `scrollTop`/measured viewport height) is hand-rolled in `GanttChart.tsx` —
  consistent with the Gantt being a locked "built from scratch" decision and with `Sparkline`
  (F4) already setting the precedent of no charting dependency. `package.json` gained no new
  runtime dependency.
- **Two independently-scrolling panes (grid, timeline) kept in sync imperatively**, not one
  scroll container — the timeline needs its own horizontal scroll (for a wide date range)
  while the grid pane stays fixed-width. Each pane's `onScroll` copies its `scrollTop` onto the
  other (`syncScroll` in `GanttChart.tsx`); a same-value assignment is a no-op in the DOM, so
  this self-limits after one hop instead of ping-ponging. Column headers and date-tick headers
  use `position: sticky; top: 0` inside their own pane rather than a second synced axis.
- **RTL is two different mechanisms, not one.** Bars, gridlines, the today-line and the grid
  column layout are positioned with `insetInlineStart` (a logical property), so the browser
  mirrors them automatically once `<html dir="rtl">` is set (F2) — no coordinate flipping in
  JS. The one thing logical properties can't reach is the dependency-arrow `<svg>`'s path
  coordinates, so that layer is mirrored the same way `Sparkline.css` (F4) already mirrors its
  polyline: `:root[dir='rtl'] .gantt-arrows { transform: scaleX(-1) }`. Verified visually — see
  below — including that mirrored arrows still point the geometrically correct direction.
- **Dependency arrows connect the CPM-correct edge per type**, not always start→finish:
  `predecessorEdge`/`successorEdge` in `ganttMath.ts` read the same FS/SS/FF/SF semantics
  `CriticalPathEngine.cs` computes from (SS/SF read the predecessor's *start*; FF/SF land on
  the successor's *finish*), so an SS or FF dependency in real data draws correctly instead of
  every arrow uniformly running bar-end to bar-start.
- **Arrows only render when both endpoints' rows are inside the current virtualization
  window.** At 10k tasks, filtering the full dependency list on every scroll event would cost
  more than the virtualization saves; `groupDependenciesByPredecessorRow` buckets dependencies
  once (`useMemo`), so a scroll only scans the visible row range. An arrow whose other end has
  scrolled off-screen simply isn't drawn — an accepted trade-off for render cost, not a bug.
- **No client-side working-calendar/weekend logic.** F7's scope line is rendering, not
  scheduling — `scheduleStart`/`scheduleFinish` arrive already correct from `ScheduleQuery.cs`;
  the Gantt only turns those dates into pixels (`ganttMath.ts`'s day-diff arithmetic, all in
  UTC to dodge local-timezone DST shifts). No weekend shading was built — not in F7's "Done
  when" line, and adding it would mean guessing at a calendar the client doesn't have access to
  (P3 owns exposing it).
- **A dev-only synthetic-data stress harness, not a seeded 10k-row project.** `gantt/
  stressData.ts` generates a shape-compatible `ScheduleResponse` (many parallel task chains,
  one deliberately the longest so critical-path highlighting has something real to show)
  entirely client-side. `ProjectWorkspacePage` swaps it in for `?stress=<n>` behind
  `import.meta.env.DEV` — never reachable in a production build. This was chosen over adding a
  10k-row generator to `PmoDemoSeed` (which runs on every dev boot against real PostgreSQL,
  per F6) because "Done when: scrolls and renders smoothly" is a rendering-layer claim the
  frontend can verify on its own, and a heavier seed would have slowed down every other
  session's dev startup for a scenario only this one needs. Documented as a decision rather
  than silently added, per CLAUDE.md's "flag open items" guidance.
- **Percent-complete is shown as an in-bar fill**, not a separate column-only number — a small
  addition beyond the literal "bars" word in scope, but it's the standard reading of "a Gantt
  bar" and reuses data (`task.percentComplete`) already on the wire.
- **Milestones render as a rotated-square diamond**, sized independently of `DAY_WIDTH`
  (`MILESTONE_SIZE`), anchored at their single date — distinct from a 1-day bar so a real
  milestone (`Go-Live` in the demo seed) doesn't look like an ordinary short task.

## How it was verified

- `npm run build` (`tsc -b && vite build`) and `npm run lint` (oxlint) — both clean, no new
  runtime dependency added.
- **Ran the real stack end to end against live local PostgreSQL** (not mocked): `dotnet run`
  from `src/Api`, `npm run dev` from `web/`, confirmed via `curl` that
  `/api/pmo/projects/{id}/schedule` still returns F6's seeded "Tenant Onboarding Revamp" tree
  (6 tasks, 6 dependencies, one non-critical branch with 3 days float, one milestone).
- **Ran the real app in a headless browser** (Playwright against the already-cached system
  Chromium) at `/pmo/projects/{id}` for that project:
  - 5 bars + 1 milestone rendered, 4 critical elements coloured with the risk token, 6
    dependency-arrow paths drawn, the today-line present — zero console errors.
  - Scrolled the timeline pane horizontally and confirmed the `Go-Live` milestone diamond and
    its incoming arrows render correctly past the initial viewport.
  - Switched to Arabic: confirmed `dir="rtl"`, the whole grid/timeline mirrored (date ticks
    running right-to-left, WBS/Task columns swapping sides, bars and dependency arrows
    mirrored and still geometrically correct), matching the light theme. Screenshot taken.
- **Stress-tested the "Done when" line directly**: navigated to `?stress=10000` (10,000
  synthetic tasks across ~100 parallel chains). Measured via Playwright:
  - Initial render (nav → first `.gantt-bar` visible): **1.4s**.
  - DOM footprint: **34 `.gantt-grid__row` / `.gantt-bar` elements mounted** regardless of
    scroll position — confirms virtualization is actually windowing, not mounting all 10k rows.
  - 40 rapid `scrollTop` jumps spanning the full 10k-row range: **530ms total**, DOM row count
    unchanged (still 34) after settling, zero console errors.
  - Screenshotted the top of the list and after a deep scroll (~row 3,750) — both rendered
    correctly with the grid/timeline still in sync.
- Dark theme: confirmed via `getComputedStyle` that `data-theme="dark"` does flip the
  underlying CSS tokens the Gantt consumes (`body` background changed from
  `rgb(233,234,238)` to `rgb(20,22,26)`), but a full-page screenshot taken immediately after
  the toggle click still rendered light — not chased further (same gap F4/F6 already left open
  for dark-theme screenshots). Since `GanttChart.css` uses only `var(--...)` tokens with no
  hardcoded colours, this is a screenshot-timing artifact, not a styling gap, but it wasn't
  re-verified with a longer wait.

## Follow-ups

- F8 owns drag-to-move, drag-resize, drag-to-link, expand/collapse and live reschedule — this
  session's Gantt is read-only, matching F6's schedule panel being read-only before it.
- No weekend/holiday shading on the timeline — P3 (calendar admin) doesn't exist yet server-side
  in an exposed-to-the-client form; revisit once a tenant's working calendar is readable from
  the API rather than only used internally by `ScheduleQuery.cs`.
- Dark-theme screenshot verification of the Gantt specifically is still open (see above) —
  low-risk given token-only styling, but worth a real screenshot once someone is already in
  the area.
- `stressData.ts`'s `?stress=` flag is dev-only convenience for re-verifying the "10k tasks"
  line by hand later (e.g. after F8 adds interaction) — not a permanent test fixture; if a real
  perf regression test is ever wanted, promote it into an actual test rather than relying on
  this manual flag.
- Week-tick date labels are the only timeline scale; there's no zoom control (day/week/month)
  — not requested by F7's scope line, but likely wanted once real users have very long
  projects, worth flagging for F9/executive-dashboard-adjacent work rather than assuming it's
  covered.
